# /docs — Документация по коду

Цель: сгенерировать или обновить документацию, чтобы код был понятен без чтения реализации. Фокус на «что и зачем», а не пересказ строк.

## Что сделать
1. Определить scope: модуль/файл/публичный API/весь проект (спросить, если неоднозначно).
2. Прочитать код в scope + существующие доки (README, docstrings) — чтобы не дублировать и обновлять, а не переписывать с нуля.
3. Сгенерировать/обновить:

## Что документировать
- **Публичный API**: каждая публичная функция/класс/метод — назначение, параметры (типы + смысл), возвращаемое значение, исключения, пример вызова.
- **Модуль/пакет**: однострочное «что делает» + как использовать (quick start).
- **Неочевидные решения**: WHY, а не WHAT (почему такой алгоритм/структура, какие ограничения).
- **README** (если scope = проект): установка, запуск, тесты, структура проекта.

## Правила стиля доков
- Язык документации — как в существующих доках проекта (определить из /context). Если нет доков — спросить или взять язык кода.
- Примеры должны быть рабочими и минимальными.
- Не пересказывать очевидное (`i++` → «инкрементирует i»). Документировать намерение и контракт.
- Обновлять существующие docstrings, а не создавать параллельные файлы без причины.

## Definition of Done
Доки покрывают весь публичный scope + примеры запускаются/корректны + стиль единый с проектом + diff просмотрен.
