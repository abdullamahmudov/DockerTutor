# /security-review — Аудит безопасности

Цель: найти уязвимости в изменениях/коде до коммита. Фокус на OWASP Top 10, секреты и зависимости.

## Что сделать
1. Определить scope: ревьюить diff (по умолчанию) или конкретные файлы/модули.
2. Пройтись по чек-листу ниже.
3. Каждое замечание — с приоритетом **Critical / High / Medium / Low** и конкретной строкой/файлом.

## Чек-лист безопасности
- **Инъекции**: SQL, NoSQL, OS-command, LDAP, template injection. Параметризованные запросы? экранирование вывода (XSS)?
- **Аутентификация/авторизация**: проверка прав на каждый ресурс? обход через IDOR? слабые пароли/hashing (bcrypt/argon2)?
- **Секреты в коде**: API-ключи, токены, приватные ключи, строки подключения с паролем. Проверить diff И git history новых файлов.
- **Валидация ввода**: все внешние данные (HTTP, файлы, CLI args) валидируются? тип/разр/формат?
- **Криптография**: нет home-made crypto, MD5/SHA1 для паролей, слабых PRNG, hardcoded IV/key.
- **Зависимости**: новые/обновлённые пакеты с известными CVE? (проверить версии).
- **Данные в логах**: не пишутся ли PII/секреты в логи и ошибки.
- **Файлы/путь**: path traversal, unsafe deserialization, eval/exec на внешнем вводе.

## Правила
- Не «чинять» во время аудита — сначала список замечаний (как /review).
- Critical/High должны быть устранены до коммита.
- Если scope большой — начать с diff и публичных точек входа (API, CLI, парсеры).

## Финальный вывод
Список уязвимостей: приоритет + файл:строка + описание + рекомендация по исправлению. Вердикт: «безопасно» / «нужны правки».
