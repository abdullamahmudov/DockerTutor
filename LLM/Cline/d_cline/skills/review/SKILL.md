# /review — Критическое ревью диффа

Цель: второй взгляд на изменения до коммита. Ловит то, что агент пропустил в потоке реализации: баги, безопасность, стиль, отклонение от задачи.

## Что сделать
1. Получить полный diff (`git diff` / `git diff --staged`). Если diff большой — читать по файлам.
2. Пройтись по чек-листу ниже для КАЖДОГО изменения.
3. Сформулировать список замечаний с приоритетом: **Blocker** (ломает/небезопасно) / **Major** (баг или отклонение) / **Minor** (стиль, имена).

## Чек-лист ревью
- **Правильность**: логика соответствует задаче? граничные случаи (null, пустые, 0, -1, большие данные)? race conditions?
- **Безопасность**: инъекции, невалидированный ввод, секреты в коде/логгах, небезопасные зависимости.
- **Ресурсы**: утечки (файлы, соединения, память), N+1 запросы, лишние циклы.
- **Согласованность**: именование и стиль как в остальном проекте? не дублирует ли существующий код?
- **Мусор**: отладочный вывод, закомментированный код, неиспользуемые импорты/переменные.
- **Тесты**: новое поведение покрыто тестами?

## Правила
- Не «чинять на лету» во время ревью — сначала список замечаний, потом (по согласованию) правки.
- Blocker/Major должны быть устранены до коммита; Minor — по решению пользователя.

## Финальный вывод
Список замечаний с приоритетом + вердикт: «можно коммитить» / «нужны правки (список)».
