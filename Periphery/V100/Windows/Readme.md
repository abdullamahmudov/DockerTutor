# Tesla V100 SXM2 на Windows: ошибка "Код 10" после перезагрузки

## 1. Проблема

При подключении Tesla V100 SXM2 к персональному ПК карта работает
корректно сразу после установки драйвера (`nvidia-smi` показывает
правильную информацию), но **после любой перезагрузки Windows**
устройство перестаёт запускаться с ошибкой:

```
Запуск этого устройства невозможен. (Код 10)
Недостаточно системных ресурсов для завершения вызова API.
```

На той же машине, в той же аппаратной конфигурации, карта **стабильно
работает под Ubuntu** — там ошибка ни разу не воспроизводилась.

### Конфигурация системы

| Компонент       | Значение |
|-----------------|----------|
| Материнская плата | Gigabyte Z790 UD AX, BIOS F17a |
| CPU / RAM         | Intel Core i7-14700K, 64 ГБ RAM |
| ОС                | Windows 11 Pro, сборка 26200 |
| GPU               | Tesla V100-SXM2-32GB |
| Подключение GPU   | PCIe-райзер SXM2 → PCIe (AliExpress), питание отдельными 6/8-pin от БП |
| Слот              | Верхний PCIe x16, линк — PCIe 3.0 x16 (после перевода из ручного Gen2 в Auto) |
| Дисплеи           | Подключены к встроенной графике Intel UHD 770 |

## 2. Ход диагностики

Проверка велась по принципу исключения — от аппаратных причин к
программным.

### 2.1 Проверка BIOS / PCIe-ресурсов
- **Above 4G Decoding** — включено
- **Re-Size BAR** — пробовали включённым и выключенным, разницы нет
- **CSM** — изначально выключен
- **VT-d** — пробовали включённым и выключенным, разницы нет
- **Fast Boot** — изначально выключен
- Отдельного пункта настройки MMIO High Base/Size и PCIe Slot
  Configuration в BIOS этой платы нет

**Результат:** ни одна настройка BIOS не повлияла на ошибку.

### 2.2 Проверка распределения PCI-ресурсов (BAR)
Сравнение вывода `lspci`/`dmesg` в Ubuntu и `nvidia-smi -q` /
диспетчера устройств в Windows:

- В Ubuntu карте стабильно выделяется `BAR1 = 0x6000000000–0x67ffffffff`
  (32 ГБ), сообщений о нехватке места или переназначении ресурсов нет.
- В Windows в рабочем состоянии в списке ресурсов фигурируют только
  BAR0 (16 МБ) и BAR3 (32 МБ) — BAR1 в 32 ГБ отдельно не отображается
  (карта работает в режиме TCC).

**Вывод:** гипотеза о нехватке 64-битного MMIO-окна не подтвердилась —
BIOS выделяет ресурсы одинаково в обеих ОС.

### 2.3 Проверка "состояния" GPU между перезагрузками
- **Холодное обесточивание** (выключение тумблера БП, ожидание,
  повторное включение) — ошибка осталась.
- **Переход Windows → Ubuntu → Windows** — в Ubuntu карта определяется
  всегда корректно, но при возврате в Windows ошибка возвращается.
- **`pnputil /restart-device`** в состоянии ошибки — команда
  отрабатывает, но карту не оживляет.
- **Remove + Rescan устройства** (без переустановки драйвера) — не
  помогает.

**Вывод:** проблема не в "залипшем" состоянии самой GPU — Linux каждый
раз поднимает карту с нуля одинаково успешно, аппаратная часть
исправна.

### 2.4 Журналы событий
- В журнале System — ошибки `nvlddmkm`, событие 14:
  `timeout error waiting for NV_UFLUSH_FB_FLUSH` (таймаут ответа GPU по
  шине).
- Целевой поиск по провайдеру `Microsoft-Windows-Kernel-PnP` не выявил
  явных конфликтов ресурсов, относящихся к видеокарте (только
  посторонние ошибки других драйверов — com0com, Voicemeeter, usbip).

### 2.5 Поиск по форумам NVIDIA
Найдены независимые отчёты (2023–2026) с идентичным сценарием: Tesla
V100 на десктопной плате, работает сразу после установки драйвера,
после перезагрузки — Код 10 с той же формулировкой. Один
из авторов перебрал тот же набор настроек BIOS (VT-d, SR-IOV, CSM,
Above 4G, Resize BAR) и те же версии драйверов вплоть до 580.xx,
включая "сертифицированный" 582.53 — без результата, в итоге перешёл
на Linux.

**Вывод: это известный, неисправленный баг Windows-драйверов NVIDIA
(ветки 5xx–58x) для Tesla V100 на десктопных платах**, а не проблема
конкретной системы, BIOS или подключения.

---

## 3. Причина (итоговый диагноз)

1. **Корневая причина** — баг в новых версиях Windows-драйвера NVIDIA
   (диапазон версий 5xx–58x): после полноценной работы драйвера в
   течение сессии он оставляет в системе некорректное состояние
   (предположительно кэш требований к ресурсам устройства в PnP —
   `LogConf`/`AllocConfig` в реестре), которое Windows использует при
   следующей "тёплой" загрузке вместо честного арбитража ресурсов с
   нуля, из-за чего устройству не выделяются ресурсы и оно падает с
   Кодом 10.

2. **Подтверждающее наблюдение**: если установить драйвер в систему в
    безопасном режиме и оттуда просто
   переходит в обычный — карта работает так же чисто, как после
   свежей установки драйвера. Это подтверждает, что триггер —
   именно факт **полной загрузки драйвера в предыдущей сессии**, а не
   что-либо в BIOS или в самой GPU.

---

## 4. Решения

### 4.1 Основное решение — откат версии драйвера
Установлен драйвер **475.06-data-center-tesla-desktop-win10-win11-64bit-dch-international**
— карта работает стабильно, включая множественные перезагрузки.

- ✅ Плюс: проблема исчезает полностью, без обходных путей
- ⚠️ Минус: эта версия поддерживает только **CUDA 11.4**, более новых
  CUDA 12.x возможностей не будет

### 4.2 Обходной путь, если нужна более новая версия драйвера (CUDA ≥ 12)
Подтверждённый рабочий приём — **удалить устройство из системы перед
перезагрузкой**, чтобы Windows не унесла в новую сессию испорченный
кэш ресурсов:

```powershell
Get-PnpDevice -FriendlyName "*Tesla*" | Disable-PnpDevice -Confirm:$false
pnputil /remove-device "PCI\VEN_10DE&DEV_1DB5&SUBSYS_124910DE&REV_A1\4&8BD6E8D&0&0008"
```

После перезагрузки устройство обнаруживается как новое, и PnP-арбитраж
ресурсов проходит с нуля — карта запускается корректно.

**Автоматизация:** приём оформлен в виде сценария завершения работы
(запускается от SYSTEM через локальную групповую политику), который:
1. проверяет через `nvidia-smi --query-compute-apps`, не выполняется
   ли сейчас нагрузка на GPU;
2. если да — пытается аккуратно остановить связанный docker-compose
   стек (`docker compose down`) и ждёт освобождения GPU;
3. в любом случае выполняет `Disable-PnpDevice` и
   `pnputil /remove-device` перед выключением;
4. логирует каждый шаг в `C:\Scripts\gpu-preshutdown.log`.

Подключается через `gpedit.msc` → Конфигурация компьютера →
Конфигурация Windows → Сценарии → Завершение работы, с увеличенным
временем ожидания сценария (Административные шаблоны → Система →
Сценарии → «Максимальное время ожидания сценариев групповой
политики»).

### 4.3 Альтернатива
Использовать карту исключительно под Linux (WSL2 с пробросом GPU,
двойная загрузка или выделенная машина) — единственная среда, где баг
не проявляется вообще.

---

## 5. Рекомендация

Если задача (llama.cpp и т.п.) допускает CUDA 11.4 — оставаться на
драйвере **475.06** как на самом надёжном варианте без каких-либо
дополнительных скриптов. Переходить на более новую версию драйвера
только при реальной необходимости в CUDA 12.x — и в этом случае
обязательно использовать автоматический сценарий удаления устройства
перед каждой перезагрузкой.
